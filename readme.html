Hari's Multicuisine Restaurant - Enterprise Microservices & GitOps Platform

Production-grade, resilient, event-driven restaurant management system running on Kubernetes (Minikube). Built with Flask REST APIs, Nginx UI, MySQL StatefulSet persistence, Kafka/Zookeeper event streaming, packaged cleanly with Helm Charts, and automated end-to-end via Argo CD GitOps continuous delivery.

Core Architecture & Delivery Stack:
Python Flask (Backend API) • Nginx Alpine (Frontend UI & Static Assets) • MySQL 8.0 (Persistent StatefulSet) • Apache Kafka & Zookeeper (Decoupled Event Backbone) • Python Consumer Worker (Async Ledger Daemon) • Helm v3 (Package Manager) • Argo CD (GitOps Declarative Reconciler).

1. High-Level System Architecture Overview

Traffic flows from the browser through Nginx NodePort, hits the Flask REST layer, persists to MySQL, produces payment events onto Apache Kafka, and streams real-time updates directly to console logs via an autonomous daemon consumer.

2. Complete Runbook: Execution from Scratch to GitOps Sync

Step 1: Start Cluster & Verify Status

# Start Minikube cluster using Docker driver
minikube start --driver=docker

# Verify node availability
kubectl get nodes

Step 2: Build Images & Load into Minikube

# Build updated backend, consumer, and frontend v1.1 (with filter coffee fix)
docker build -t restaurant-backend:v1.0 ./backend
docker build -t restaurant-payment-consumer:v1.0 ./consumer
docker build -t restaurant-frontend:v1.1 ./frontend

# Load images directly into Minikube cache
minikube image load restaurant-backend:v1.0
minikube image load restaurant-payment-consumer:v1.0
minikube image load restaurant-frontend:v1.1

Step 3: Deploy Helm Chart

# Deploy all tiers using single Helm chart command
helm upgrade --install haris-restaurant ./helm/restaurant-chart

# Seed database schema & menu items catalog into MySQL pod
Get-Content database\schema.sql | kubectl exec -i mysql-0 -- mysql -u restaurant_user -pAdmin@123 restaurant_db

Step 4: Launch Web UI & Consumer Real-Time Log Stream

# Terminal 1: Stream Kafka payment consumer receipts
kubectl logs -f -l app=payment-consumer

# Terminal 2: Expose frontend to web browser
minikube service frontend-service-nodeport

Step 5: Setup Argo CD GitOps Continuous Delivery

# Apply Argo CD Application custom resource
kubectl apply -f argocd-application.yaml

# Port forward Argo CD dashboard server to localhost:8080
kubectl port-forward svc/argocd-server -n argocd 8080:443

4. Deep Dive: What is Kafka & Zookeeper?

In traditional applications, if the backend attempts to call the database, billing service, and notification services synchronously, any downstream slowness causes the entire user interface to freeze. Apache Kafka and Zookeeper decouple these layers into an asynchronous, high-throughput event streaming pipeline.

What does Apache Kafka do?

Kafka acts as a distributed, append-only commit log (message broker). When an order is paid, the backend doesn't wait for reports to generate or ledgers to balance; it immediately publishes a small JSON payload to the order-payments topic in Kafka and finishes the user's HTTP request instantly.

What does Zookeeper do?

Zookeeper acts as the cluster coordinator and brain. It monitors the health of Kafka brokers, maintains configuration metadata, handles leader election for topic partitions, and alerts Kafka if any node fails.
